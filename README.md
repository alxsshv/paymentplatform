
### 📄 Концепция системы: Event-Driven Payment Platform (Мини-ядро платежей)

**Назначение:**
Платформа предназначена для обработки внутренних транзакций между счетами пользователей (P2P-переводы, пополнения и списания) с гарантией финансовой консистентности, высокой доступности и полной аудируемости.

**Ключевые бизнес-возможности (MVP):**
1. **Управление счетами:** Создание виртуальных счетов пользователей с фиксацией баланса.
2. **Прием платежных инструкций:** Получение команд на перевод средств от внешних систем (например, API Gateway) или пользователей.
3. **Валидация и фандинг:** Проверка достаточности средств, блокировка (холдирование) суммы и списание.
4. **Исполнение транзакций:** Генерация финансовых событий (эквити-записей) о成功ном или неуспешном переводе.
5. **Асинхронное оповещение:** Отправка уведомлений об изменении статуса платежа другим сервисам (уведомления, фрод-мониторинг, биллинг).

**Архитектурные принципы (Best Practices):**
*   **Event-Driven:** Сервис не выполняет синхронные HTTP-запросы к другим сервисам для уведомлений. Все общение — через Kafka.
*   **Idempotency:** Каждая транзакция имеет уникальный `idempotencyKey`. Повторная отправка одной и той же команды не приведет к двойному списанию средств.
*   **Immutability (Неизменяемость):** Финансовые записи (транзакции, записи в ledger) никогда не обновляются (`UPDATE`). Создаются только новые записи (`INSERT`) — паттерн Event Sourcing / Append-Only.
*   **Точность:** Деньги хранятся в минорных единицах (`long`, центы/копейки), никаких `double` или `float`.
*   **Outbox Pattern:** Для обеспечения консистентности между базой данных PostgreSQL и Kafka (избежание dual-write проблемы) мы будем использовать паттерн Transactional Outbox.

### Функциональные возможности (Features)

Наш MVP будет включать следующие ключевые функции:

1. **Прием платежной инструкции (Initiate Payment):**
    - Внешний клиент (через REST API) отправляет команду на перевод средств между двумя счетами.
    - Система валидирует запрос и сразу возвращает `202 Accepted`, означающий, что команда принята в обработку (асинхронный паттерн).

2. **Валидация и проверки (Authorization):**
    - Проверка существования счетов (`fromAccount`, `toAccount`).
    - Проверка достаточности средств на счете отправителя.
    - Проверка статуса счетов (не заблокированы ли они).

3. **Исполнение транзакции (Execution & Ledgering):**
    - Списание средств со счета отправителя.
    - Зачисление средств на счет получателя.
    - Фиксация записи в журнале транзакций (Ledger) с уникальным `idempotencyKey`.

4. **Асинхронное оповещение (Event Publishing):**
    - Генерация события об успешном или неуспешном платеже.
    - Отправка события в Kafka для других микросервисов (уведомления, антифрод, аналитика).

5. **Обработка событий внешними сервисами (Notification):**
    - Микросервис `notification-service` читает события из Kafka и имитирует отправку email/SMS клиенту.

6. **Кеширование балансов (Caching):**
    - Redis используется для кеширования текущих балансов счетов для быстрого доступа при валидации (паттерн Cache-Aside).

### Архитектура и потоки данных (Как это будет работать)

В основе лежит паттерн **Event-Driven Architecture** с использованием **Transactional Outbox** для надежной отправки событий.

#### Компоненты системы:
- **PostgreSQL (БД платежного ядра):** Источник истины (Source of Truth). Хранит счета, балансы и историю транзакций.
- **Redis (Кеш):** Хранит актуальные балансы счетов для быстрой проверки.
- **Kafka (Брокер сообщений):** Транспорт для асинхронных событий.

#### Поток выполнения платежа (Happy Path):

1. **REST API Request:**
    - Клиент отправляет `POST /api/v1/payments` с `{ fromAccount, toAccount, amount, idempotencyKey }`.

2. **Синхронная обработка в `payment-core`:**
    - Проверка `idempotencyKey` в кеше Redis (или БД). Если ключ уже обработан — возвращаем результат предыдущей операции.
    - Чтение баланса отправителя из Redis. Если средств недостаточно — генерируем событие `PaymentRejected` (пишем в Outbox) и возвращаем `402 Payment Required`.
    - Если средств достаточно, открываем **DB-транзакцию** (PostgreSQL):
        - Делаем `SELECT ... FOR UPDATE` счетов в БД (блокировка от конкурентных переводов).
        - Списываем `amount` с `fromAccount`, зачисляем на `toAccount`.
        - Записываем лог в таблицу `transactions`.
        - Записываем событие `PaymentCompleted` в таблицу `outbox_events` (Outbox pattern).
    - Коммитим DB-транзакцию. (Если коммит прошел — деньги списаны, событие готово к отправке).
    - Обновляем баланс в Redis (инвалидация или обновление).
    - Возвращаем клиенту `202 Accepted`.

3. **Асинхронная отправка в Kafka (Outbox Relay):**
    - Фоновый процесс (или Kafka producer) читает записи из таблицы `outbox_events` со статусом `PENDING`.
    - Отправляет их в Kafka-топик `payments.events.v1`.
    - Меняет статус в таблице на `SENT` (или удаляет, зависит от реализации).

4. **Асинхронная обработка в `notification-service`:**
    - `notification-service` подписан на топик `payments.events.v1`.
    - Читает событие `PaymentCompleted`.
    - Формирует текст уведомления и "отправляет" (логирует в консоль).
    - Коммитит offset в Kafka.

### План реализации

#### Этап 1: Фундамент и REST API (Текущий)
- Настроить Gradle, CI, Docker (Сделано).
- Создать DTO и REST-контроллер для приема платежей.
- Настроить базовую валидацию (`@Valid`, `jakarta.validation`).

#### Этап 2: База данных и бизнес-логика
- Создать схемы БД (счета, транзакции, outbox) через Flyway/Liquibase.
- Реализовать сервисный слой `PaymentService` с DB-транзакциями.
- Настроить `@Transactional` и блокировки счетов (`pessimistic locking`).

#### Этап 3: Внедрение Kafka (Outbox Pattern)
- Настроить Kafka Producer в `payment-core`.
- Реализовать таблицу `outbox_events` и процесс отправки сообщений.
- Создать топики в Kafka программно (через `KafkaAdmin`).
- Настроить `notification-service` как Kafka Consumer.
- Реализовать ручной коммит offset'ов и базовую обработку ошибок.

#### Этап 4: Производительность и Redis
- Подключить Spring Data Redis к `payment-core`.
- Реализовать Cache-Aside: чтение баланса из кеша, обновление при транзакции.
- Настроить TTL и стратегию инвалидации кеша.

#### Этап 5: Эволюция контрактов (Avro)
- Добавить Schema Registry в Docker Compose.
- Создать Avro-схемы для событий (`PaymentCompleted`, `PaymentRejected`).
- Перевести продюсера и консьюмера на Avro-сериализацию.
- Настроить совместимость схем (backward compatibility).

#### Этап 6: Надежность и Exactly-Once
- Включить идемпотентного продюсера.
- Включить Kafka-транзакции для Outbox-реля (EOS - Exactly Once Semantics).
- Настроить Dead Letter Topic (DLT) для сообщений, которые не удалось обработать в `notification-service`.

### Схема базы данных (Предварительная)

Для понимания, как мы будем хранить данные:

- **`accounts`**: `id` (UUID), `customer_id` (UUID), `balance` (BIGINT - в центах), `currency` (VARCHAR), `status` (VARCHAR).
- **`transactions`**: `id` (UUID), `from_account_id` (UUID), `to_account_id` (UUID), `amount` (BIGINT), `status` (VARCHAR), `idempotency_key` (VARCHAR, UNIQUE), `created_at` (TIMESTAMP).
- **`outbox_events`**: `id` (UUID), `aggregate_id` (UUID), `event_type` (VARCHAR), `payload` (JSONB), `status` (VARCHAR), `created_at` (TIMESTAMP).

### Управление счетами: REST API (Путь пользователя)

В `payment-core` реализуем (или позже выделим в `account-service`) REST API для:
- **Открытия счета:** `POST /api/v1/accounts` (создает счет с нулевым балансом).
- **Закрытия счета:** `PATCH /api/v1/accounts/{id}/close` (меняет статус на `CLOSED`, запрещает транзакции).
- **Пополнения счета:** `POST /api/v1/accounts/{id}/deposit` (увеличивает баланс, эмулируя внесение наличных или банковский перевод).

*Примечание по архитектуре:* В строгой архитектуре `payment-core` должен только списывать/зачислять деньги при переводах, а пополнение (deposit) — это отдельный домен. 
Но для MVP пока оставим это в одном сервисе, чтобы не раздувать количество микросервисов слишком рано.


### Как это ложится на архитектуру (Event-Driven)
В идеальной архитектуре:
1. Пришел REST-запрос `POST /accounts` -> Сервис создает запись в БД -> Пишет событие `AccountOpened` в Kafka.
2. Пришел REST-запрос `POST /accounts/{id}/deposit` -> Сервис увеличивает баланс -> Пишет событие `AccountFunded` в Kafka.

Но так как мы идем шаг за шагом, пока не будем усложнять `payment-core` событиями по открытию счетов:
1. Миграции (Flyway) для создания таблиц и тестовых счетов.
2. REST API для переводов.
3. REST API для пополнения счета (чтобы эмулировать приход денег извне).
