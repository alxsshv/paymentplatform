
### 📄 Концепция системы: Event-Driven Payment Platform (Мини-ядро платежей)

**Назначение:**
Платформа предназначена для обработки внутренних транзакций между счетами пользователей (P2P-переводы, пополнения и списания) с гарантией финансовой консистентности, высокой доступности и полной аудируемости.

**Ключевые бизнес-возможности (MVP):**
1. **Управление счетами:** Создание виртуальных счетов пользователей с фиксацией баланса.
2. **Прием платежных инструкций:** Получение команд на перевод средств от внешних систем (например, API Gateway) или пользователей.
3. **Валидация и фандинг:** Проверка достаточности средств, блокировка (холдирование) суммы и списание.
4. **Исполнение транзакций:** Генерация финансовых событий (эквити-записей) о成功ном или неуспешном переводе.
5. **Асинхронное оповещение:** Отправка уведомлений об изменении статуса платежа другим сервисам (уведомления, фрод-мониторинг, биллинг).

**Архитектурные принципы (Best Practices):**
*   **Event-Driven:** Сервис не выполняет синхронные HTTP-запросы к другим сервисам для уведомлений. Все общение — через Kafka.
*   **Idempotency:** Каждая транзакция имеет уникальный `idempotencyKey`. Повторная отправка одной и той же команды не приведет к двойному списанию средств.
*   **Immutability (Неизменяемость):** Финансовые записи (транзакции, записи в ledger) никогда не обновляются (`UPDATE`). Создаются только новые записи (`INSERT`) — паттерн Event Sourcing / Append-Only.
*   **Точность:** Деньги хранятся в минорных единицах (`long`, центы/копейки), никаких `double` или `float`.
*   **Outbox Pattern:** Для обеспечения консистентности между базой данных PostgreSQL и Kafka (избежание dual-write проблемы) мы будем использовать паттерн Transactional Outbox.

### 🌿 Наш рабочий процесс (GitFlow)

Для имитации командной разработки мы будем использовать следующий пайплайн:

1. **`main`** — стабильная ветка, готовая к production-релизу. Здесь всегда рабочий код.
2. **`develop`** — ветка интеграции. Сюза сливаются фичи.
3. **`feature/*`** — ветки для разработки конкретных задач (например, `feature/payment-kafka-producer`, `feature/redis-balance-cache`).
4. **`release/*`** — ветки подготовки к релизу (фиксы багов, обновление версий).
5. **`hotfix/*`** — срочные исправления в production.

### 🏗️ План реализации MVP (Первые шаги)

**Этап 1: Фундамент и бизнес-логика (Текущий)**
*   Создание структуры multi-module проекта Maven/Gradle.
*   Настройка Docker Compose (PostgreSQL, Kafka, Redis, Kafka-UI).
*   Разработка DTO и базовой логики `PaymentService` (без Kafka).

**Этап 2: Изолированность через Kafka**
*   Разделение монолита на `Payment-Core` (обработка) и `Notification-Service` (слушатель).
*   Внедрение JSON-сериализации в Kafka.
*   Ручной коммит оффсетов, базовая обработка ошибок.

**Этап 3: Performance & Patterns**
*   Внедрение Redis для кеширования балансов (read-through/write-behind).
*   Реализация паттерна Outbox.
*   Внедрение DLT (Dead Letter Topic) для невалидных платежей.

**Этап 4: Эволюция контрактов**
*   Переход с JSON на Avro + Schema Registry.
*   Настройка совместимости схем (backward compatibility).
